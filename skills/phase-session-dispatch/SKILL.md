# phase-session-dispatch

총괄 세션(매니저)은 진행도만 관리하고, 승인된 phase의 실제 작업은 phase 전용 세션에 맡긴다. 각 phase 세션은 plan·execute를 시작하기 전에 `jev-model-routing` 스킬로 에이전트·task의 모델을 정한다.

## 0. 언제 쓰나

- 매니저가 discuss / plan / execute 중 하나를 dispatch하려는 순간. 인라인 Skill 호출이나 `Agent(run_in_background)` 대신 이 절차를 따른다.
- 사용자가 "phase 12, 13 세션으로 돌려줘"처럼 phase 번호를 지정했을 때.

## 1. 원칙

1. **승인한 phase만 세션을 만든다.** 사용자가 번호로 허용한 phase만 대상이다. 메뉴의 "Continue"처럼 여러 액션이 묶인 선택이면 대상 목록을 한 줄로 보여주고 확인받은 뒤 만든다. 추천된 phase도 승인 전에는 만들지 않는다.
2. **phase 하나 = 세션 하나.** 승인된 수만큼만 만든다. 총괄 세션은 그대로 남는다.
3. **총괄은 진행도만 수정한다.** 로드맵·상태 문서·설계 문서·지식 그래프 같은 진행 기록은 총괄만 고친다. 논의·plan·실행·검증 같은 세부는 phase 세션이 한다.
4. **하위 결과는 사용자가 검증한 뒤 반영한다.** 총괄은 보고를 받아 반영만 하고 결과물을 다시 감사하지 않는다.

## 2. 만들기 전 확인 (총괄)

- `git status`로 커밋되지 않은 변경을 본다. worktree 세션은 마지막 커밋 기준으로 시작하므로, 그 변경이 필요하면 사용자에게 먼저 커밋할지 묻는다.
- 승인된 phase끼리 파일이나 선후 의존이 겹치는지 로드맵으로 확인한다. 겹치면 순서를 사용자에게 묻는다.
- 같은 phase의 세션이 이미 있는지 `list_sessions`로 본다. 있으면 새로 만들지 않고 그 세션에 `SendMessage`로 이어 준다.

## 3. 세션 만들기

phase마다 `mcp__ccd_session__start_session`을 호출한다. 호출 직전 메시지에 굵은 제목 한 줄과 한 문장으로 무엇을 하는지 적는다. 둘 이상이면 먼저 `mark_chapter`로 묶는다.

- `initiation`: `user_asked` (사용자가 승인했으므로)
- `context`: `fresh`
- `use_worktree`: `true` (쓰기 작업이고 phase끼리 병렬이므로)
- 제목: `Phase {NN} {phase 이름}`

### 브리프 템플릿

```
Phase {NN} ({이름}) 담당 세션이다. 총괄 세션이 사용자 승인 후 만들었다.

먼저 읽을 것: 프로젝트 지침 파일(CLAUDE.md, AGENTS.md), 상태 문서, 로드맵의 이 phase 항목, phase 폴더 안의 문맥·계획 문서(있는 것).
요구사항 ID: {IDs}
시작 단계: {discuss | plan | execute | verify}  (현재 상태: {상태 문서 기준 한 줄})

규칙
- 수정 범위는 이 phase 폴더와 이 phase의 코드·테스트뿐이다.
- 상태 문서, 로드맵, 요구사항 목록, 설계 문서, 지식 그래프는 수정하지 않는다. 총괄이 반영한다.
- 논의·plan 승인·검증은 사용자와 이 세션에서 직접 한다. 결정이 필요하면 사용자에게 묻는다.
- 에이전트·task 모델 배정은 jev-model-routing 스킬을 따른다. 사용자가 모델을 지정했다면 그 값이 우선이다.
- 버그가 나오면 이 프로젝트의 버그 처리 절차를 따른다.
- 사용자가 검증을 끝냈다고 말한 뒤에만 총괄에 보고한다. 보고에는 phase, 브랜치, 충족한 요구사항 ID, 남은 이슈, 완료한 plan 수를 한 덩어리로 적는다.
```

## 4. 모델 배정 연결 (phase 세션 안에서)

phase 세션이 planner·executor·checker 같은 에이전트를 띄우기 직전마다 다음 순서로 한다.

1. `jev-model-routing` 스킬을 따라 역할·plan·task별 모델과 채널(Claude / Codex)을 정한다.
2. 호출 직전에 사용자에게 도구와 모델·추론 강도를 한 줄로 알린다.
3. Codex를 호출했다면 실행 로그 첫머리의 `model:` 줄이 명시한 모델과 같은지 확인한다. 다르면 즉시 중단하고 보고한다.
4. 결정은 plan 파일에 기록해 같은 입력으로 다시 Jev를 부르지 않는다.

## 5. 보고를 받은 뒤 (총괄)

1. 보고가 사용자의 "검증 끝"을 거쳤는지 확인한다. 아니면 반영하지 않고 사용자에게 묻는다.
2. 진행 기록을 갱신한다: 로드맵의 phase 진행률 → 상태 문서 → 요구사항 추적 → 설계 문서 순서로 맞춘다. 프로젝트에 지식 그래프가 있으면 갱신 명령을 돌린다.
3. 동기화 결과만 커밋한다. phase 브랜치는 병합하지 않는다.
4. 브랜치 병합은 사용자가 직접 지시할 때만 한다. 병합 전에는 `refs/heads/...` 전체 이름으로 브랜치를 알리고 묻는다.
5. 매니저 화면으로 돌아가 다음 승인을 기다린다.

## 6. 하지 않는 것

- 승인 없이 phase 세션을 만들거나, 승인된 수를 넘겨 만드는 것.
- 총괄에서 phase의 세부 논의나 plan 결정을 대신하는 것.
- 하위 세션의 브랜치를 사용자 지시 없이 병합하거나 push하는 것.
- 보고가 돌아오지 않는 클라우드 세션을 쓰는 것 (사용자가 요청할 때만 예외).
